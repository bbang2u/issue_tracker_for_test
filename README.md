# Issue Tracker API

Spring Boot 기반의 간단한 이슈 관리 API 프로젝트입니다.  
이슈 생성, 전체 조회, 단건 조회, 상태 변경 기능을 제공합니다.  
단순 기능 구현에 그치지 않고, Postman·H2·Jira를 활용해 QA 관점에서 정상/비정상 API 테스트와 결함 등록까지 수행해보았습니다.

---

## 1. 프로젝트 목적

이 프로젝트는 백엔드 API 구현 연습과 함께,  
QA 실무에서 중요한 다음 흐름을 직접 수행해보기 위해 만들었습니다.

- API 기능 구현
- 입력값 검증 및 예외 처리
- Postman 기반 정상/비정상 테스트
- H2 DB 직접 검증
- Jira 기반 결함 등록 및 추적

즉, **개발 + QA 사이클을 함께 연습하기 위한 미니 프로젝트**입니다.

---

## 2. 주요 기능

- 이슈 생성
- 전체 이슈 조회
- 특정 이슈 조회
- 이슈 상태 변경
- 제목 필수값 검증
- Enum 기반 상태값 제한
- 전역 예외 처리(JSON 에러 응답)

---

## 3. 기술 스택

- Java 17
- Spring Boot
- Spring Data JPA

- Jakarta Validation

---

## 4. 이슈 상태값

현재 지원하는 상태값은 아래 4가지입니다.

- `TO_DO`
- `IN_PROGRESS`
- `IN_REVIEW`
- `DONE`

---

## 5. API 목록

| Method | Endpoint | 설명 |
|---|---|---|
| POST | `/issues` | 이슈 생성 |
| GET | `/issues` | 전체 이슈 조회 |
| GET | `/issues/{id}` | 특정 이슈 조회 |
| PATCH | `/issues/{id}/status` | 이슈 상태 변경 |

## 7. 실행 방법

### 7-1. 애플리케이션 실행

프로젝트 루트 경로에서 아래 명령어로 실행합니다.

```bash
./gradlew bootRun
```

또는 IDE(IntelliJ 등)에서 Spring Boot 애플리케이션을 직접 실행할 수 있습니다.

### 7-2. 기본 접속 정보

* Server: `http://localhost:8080`
* H2 Console: `http://localhost:8080/h2-console`

### 7-3. H2 Console 접속

H2 Console 접속 시 애플리케이션 설정값에 맞춰 접속합니다.
본 프로젝트는 In-Memory H2 Database를 사용하므로, 애플리케이션 실행 중에만 데이터가 유지됩니다.

### 7-4. 테스트 실행 방법

API 테스트는 Postman으로 수행했습니다.
테스트 대상 엔드포인트는 아래 4개입니다.

* `POST /issues`
* `GET /issues`
* `GET /issues/{id}`
* `PATCH /issues/{id}/status`

## 8. QA 테스트 요약

이번 프로젝트에서는 단순 API 구현에 그치지 않고,
**QA 관점에서 정상/비정상 API 테스트 → 결함 등록 → 수정 → 재검증** 흐름을 한 번 수행했습니다.

### 8-1. 테스트 범위

대상 API:

* `POST /issues`
* `GET /issues`
* `GET /issues/{id}`
* `PATCH /issues/{id}/status`

검증 관점:

* 정상 요청 처리
* 필수값 검증
* 존재하지 않는 리소스 조회
* 상태 변경 처리
* API 응답과 DB 반영 상태 일치 여부

### 8-2. 테스트 실행 결과

총 **8개 테스트 케이스**를 실행했습니다.

* Pass: 7건
* Fail: 1건

실행 결과:

* TC-01: Pass
* TC-02: Pass
* TC-03: Pass
* TC-04: Pass
* TC-05: Fail
* TC-06: Pass
* TC-07: Pass
* TC-08: Pass

### 8-3. 발견된 주요 결함

가장 대표적인 실패 케이스는 **존재하지 않는 ID 조회 시 기대값 404 대신 500이 반환된 문제**였습니다.

이 결함은 Jira에 Bug 티켓으로 등록했고,
원인 분석 후 코드를 수정한 뒤 재테스트를 수행했습니다.

### 8-4. 재검증 결과

수정 후 다시 테스트한 결과,
존재하지 않는 ID 조회 시 기대한 **404 Not Found** 응답이 정상적으로 반환되는 것을 확인했습니다.

즉, 이번 프로젝트에서는 아래 흐름을 실제로 수행했습니다.

* Jira 버그 등록

* 재검증
* DB 상태 확인

## 9. 대표 트러블슈팅

### 문제

존재하지 않는 ID로 이슈를 조회할 때,
기대한 결과는 `404 Not Found`였지만 실제로는 `500 Internal Server Error`가 반환되었습니다.

### 원인

서비스 레이어에서 존재하지 않는 ID 조회 시 `IllegalArgumentException`을 발생시키고 있었는데,
이 예외는 자동으로 404 상태 코드로 매핑되지 않았습니다.
그 결과 의도와 다르게 500 오류 응답이 반환되었습니다.

### 해결

예외를 단순 일반 예외로 두는 대신,
리소스가 존재하지 않는 상황이라는 의미를 명확히 표현하기 위해
`ResponseStatusException(HttpStatus.NOT_FOUND, ...)` 방식으로 수정했습니다.

### 결과

수정 후 재테스트에서 존재하지 않는 ID 조회 시 **404 Not Found**가 정상적으로 반환되는 것을 확인했습니다.

### 배운 점

이 경험을 통해 예외가 발생한다는 사실만 중요한 것이 아니라,
**그 예외가 클라이언트에게 어떤 HTTP 상태 코드와 의미로 전달되는지까지 설계해야 한다**는 점을 배웠습니다.

## 10. 구조 설명

이 프로젝트는 단순한 Issue Tracker API를 목표로 하되,
입력 검증과 예외 처리, 상태값 제한까지 포함해 **테스트 가능한 최소 API 구조**를 만드는 데 초점을 맞췄습니다.

### 10-1. 핵심 구성 요소

* **Issue Entity**

  * 이슈 데이터를 표현하는 핵심 엔티티
* **IssueStatus Enum**

  * 상태값을 자유 문자열이 아니라 고정된 Enum으로 제한
  * 지원 상태:

    * `TO_DO`
    * `IN_PROGRESS`
    * `IN_REVIEW`
    * `DONE`
* **Controller**

  * 클라이언트 요청을 받아 API 엔드포인트를 제공
* **Service**

  * 이슈 생성, 조회, 상태 변경 등 핵심 비즈니스 로직 담당
* **Repository**

  * DB 접근 담당
* **Global Exception Handler**

  * 예외를 JSON 형태의 일관된 응답으로 반환하기 위한 전역 예외 처리

### 10-2. 설계 의도

이 프로젝트에서는 특히 아래 3가지를 중요하게 봤습니다.

1. **입력 검증**

   * `title` 필수값 검증을 추가해 잘못된 요청을 조기에 차단

2. **상태값 제한**

   * 상태를 문자열로 자유롭게 받지 않고 Enum으로 제한해 데이터 정합성 확보

3. **예외 처리 일관성**

   * `@RestControllerAdvice` 기반 전역 예외 처리 적용
   * 잘못된 요청과 리소스 미존재 상황에 대해 의미 있는 HTTP 응답 반환

### 10-3. API 흐름

현재 프로젝트의 핵심 API 흐름은 아래와 같습니다.

* `POST /issues`

  * 새로운 이슈 생성
* `GET /issues`

  * 전체 이슈 조회
* `GET /issues/{id}`

  * 특정 이슈 조회
* `PATCH /issues/{id}/status`

  * 특정 이슈 상태 변경

### 10-4. QA 관점에서의 의미

이 구조는 단순 CRUD API 예제가 아니라,
**정상 케이스 / 비정상 케이스 / 상태 변경 / 예외 처리 / DB 반영 확인**까지 테스트할 수 있도록 의도한 구조입니다.

따라서 이 프로젝트는

* 백엔드 API 구현 연습
* Postman 기반 API 테스트
* H2 기반 DB 검증
* Jira 기반 버그 등록 및 추적
  을 함께 연습할 수 있는 미니 프로젝트로 활용했습니다.

## 11. 회고

이번 프로젝트를 통해 단순히 API를 구현하는 것에서 끝나는 것이 아니라,
실제로 테스트하고, 실패 케이스를 발견하고, 원인을 분석하고, 수정 후 다시 검증하는 과정까지 경험할 수 있었습니다.

특히 아래 세 가지를 배웠습니다.

1. 예외 처리 방식에 따라 같은 실패 상황도 500과 404처럼 전혀 다른 의미의 응답이 될 수 있다는 점
2. Postman 응답 확인만이 아니라 H2 DB 확인까지 함께 해야 테스트 결과를 더 신뢰할 수 있다는 점
3. QA는 결함을 발견하는 것에서 끝나는 것이 아니라, 등록·수정·재검증까지 흐름을 닫는 일이 중요하다는 점
